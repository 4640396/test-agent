## 架构设计

### 1. 执行历史存储（runs.jsonl）

路径：`.test-agent/cases/<projectHash>/<caseId>/runs.jsonl`

每次执行后追加一行 JSON：`{ "passed": true/false, "timestamp": "ISO8601" }`

- `recordRun(baseDir, caseId, passed)` — 追加记录
- `loadRuns(baseDir, caseId, limit)` — 读取最近 N 条（默认窗口 10）
- 损坏行自动跳过，不影响其他记录

### 2. 可疑用例识别（双保险）

可疑 = 诊断标 flaky **或** 近10次通过率 < 90%（且历史 >= 3 次）

- `identifySuspiciousReasons(runs, diagnosisCategory, config)` — 返回可疑原因列表
- 历史不足（<3 次）→ 不按历史判可疑，仅靠诊断标 flaky 触发
- `isSuspiciousByHistory(runs, config)` — 历史通过率 < 90% 且 >= 3 次记录

### 3. 重跑判定（PRD 6.5 场景 A）

对可疑用例重跑 5 次，通过率 > 0% 且 < 80% 判 flaky：

```
detectFlaky(runsBaseDir, caseId, caseTitle, diagnosisCategory, rerunExecutor)
  → 读取历史 → 识别可疑 → 重跑 N 次 → 判定 flaky → 返回 FlakyRecord
```

**P2 修复（round 2）**：0% 通过率 = 持续失败 = 真 bug，不判 flaky。flaky 定义为"时过时不过"，需至少 1 次重跑通过才判 flaky。条件改为 `rerunPassRate > 0 && rerunPassRate < threshold`。

FlakyRecord 包含客观数据：
- `rerunResults: boolean[]` — 每次重跑 pass/fail
- `rerunPassRate: number` — 重跑通过率
- `historyPassRate: number` — 历史通过率
- `historyCount: number` — 历史记录数
- `reason: string` — 判定依据（如"5 次重跑 2 过 3 失，通过率 40% < 80%"或"5 次重跑全失，通过率 0% → 持续失败（真 bug），不判 flaky"）

### 4. 重跑执行器（RerunExecutor）

`createRerunExecutor(testToolContext, usedTools)` 根据执行阶段使用的测试工具创建：

- **node_test**：调 `runNodeUnitTests` + `failedCases` 做用例级匹配
- **maven_test**：调 `runMavenUnitTests` + 聚合结果（套件通过→用例通过）
- **playwright_test**：调 `runPlaywrightUiTests` + `uiSteps` 做用例级匹配
- 无匹配工具 → 返回 undefined（Flaky 检测降级跳过，不阻断主流程）

用例级匹配策略：套件通过→该用例通过；套件失败→检查用例标题是否在失败列表中（includes 模糊匹配）。

### 5. 质量门禁隔离（PRD 6.5 场景 C）

`evaluateQualityGate(totalCases, failedCases, flakyRecords)`：

- 非 flaky 失败 → 计入主门禁，决定 pass/fail
- flaky 失败 → 隔离不计入主门禁
- flaky 通过 → 标记但不阻断

结果 `QualityGateResult`：
- `status: 'passed' | 'failed'` — 主门禁状态
- `passed/failed` — 主门禁通过/失败数（不含 flaky 隔离）
- `flakyIsolated` — flaky 隔离数
- `flakyFailed` — flaky 失败数（不计入门禁）
- `summary` — 门禁摘要文本

### 6. Runner 集成（runExecute）

在诊断块之后、`return result` 之前：

1. **记录执行历史**：对全量用例，基于诊断结果判定 pass/fail，追加到 runs.jsonl
   - P1 修复：非 UI 测试若 failedCases 使用合成名无法按用例标题归因 → 跳过本次历史记录，避免写入错误的"全过"数据
2. **可疑用例筛选**：诊断标 flaky 或历史 < 90% 的用例
   - P2d 修复：不仅在本轮失败时触发，也检测历史不稳定但本轮通过的用例（PRD 场景 B）
3. **重跑检测**：对可疑用例调 `detectFlaky`，重跑 5 次
4. **门禁隔离**：调 `evaluateQualityGate`，flaky 失败隔离出主门禁
5. **报告填充**：`result.report.flakyCases` + `result.report.qualityGate`

全流程 try-catch 包裹，异常降级跳过不阻断主流程。

### 7. P1 修复：用例级名称匹配（round 2）

**问题**：非 UI 测试（node_test/maven_test）的诊断输入使用合成聚合名（如 `"node_test 失败用例"`），导致：
- (a) 历史记录将所有用例标记为已通过（failedNames 不匹配 case title）
- (b) 基于诊断的可疑识别从未匹配（diagnosisByTitle 键不匹配 case title）
- 综合结果：Flaky 检测对非 UI 测试是空操作

**修复**：
1. `TestToolDetails` 增加 `failedCases` 可选字段，`node-test.ts` 从 validator TAP 解析结果透传失败用例名称
2. 诊断输入构建时，用模糊匹配（includes 双向）将测试输出的失败名称匹配到 `cases[].title`，使 `failedCases[].name` 使用真实用例标题
3. 历史记录增加 `canAttributeFailures` 守卫：无法按用例标题归因失败时跳过记录，避免写入错误数据
4. maven_test 无 per-case 数据 → 仍用合成名，Flaky 检测降级（PRD 6.7 已知限制）

## 验收对照

### PRD 6.5 场景 A：重跑判定 flaky ✅

- 输入：诊断标 flaky 的用例
- 重跑 5 次，2 过 3 失 → `isFlaky=true`，`reason="5 次重跑 2 过 3 失，通过率 40% < 80%"`
- 验收点：flaky 标记附客观数据（rerunResults + rerunPassRate），非 LLM 主观判断
- 测试：`flaky.test.ts > detectFlaky > 场景A: 重跑判定 flaky`

### PRD 6.5 场景 B：历史通过率触发 ✅

- 输入：7 过 3 失（70% < 90%），历史 >= 3 次
- 自动标记可疑 → 触发重跑确认
- 验收点：阈值可配（FlakyConfig），触发有据（suspiciousReasons 含通过率数据）
- P2d 修复：本轮全过时也检测历史不稳定用例
- 测试：`flaky.test.ts > detectFlaky > 场景B: 历史通过率触发`

### PRD 6.5 场景 C：flaky 隔离不阻断门禁 ✅

- 输入：50 用例，3 个 flaky（1 失败），无其他失败
- 门禁判定"通过（3 flaky 隔离，1 失败不计入）"
- 验收点：flaky 失败不拉低门禁通过率，但可见可追踪（flakyCases 单独列出）
- 测试：`quality-gate.test.ts > 场景C（精确）`

## 配置参数（FlakyConfig）

| 参数 | 默认值 | 说明 |
|------|--------|------|
| historyPassRateThreshold | 0.9 (90%) | 历史通过率阈值，低于判可疑 |
| minHistoryForJudgment | 3 | 历史最少记录数，不足不判 |
| rerunCount | 5 | 重跑次数 |
| rerunPassRateThreshold | 0.8 (80%) | 重跑通过率阈值，低于判 flaky（需 > 0%） |
| historyWindowSize | 10 | 历史窗口大小 |

## 降级策略

- Flaky 检测异常 → 降级跳过，不阻断主测试结果
- 无可用重跑执行器 → 标注"未执行重跑"，不判 flaky
- 重跑执行异常 → 计为失败（保守），但 0% 通过率不判 flaky（P2 修复）
- 历史不足 → 不按历史判可疑，靠诊断+重跑双保险
- 非 UI 测试无法按用例标题归因失败 → 跳过历史记录（P1 修复）

## 控制面零改动

全部功能在 Worker/Agent 层完成，不依赖 Java 控制面/Flyway/MySQL：
- 历史存储：纯文件系统（runs.jsonl）
- 可疑识别：本地计算
- 重跑执行：直接调 validator 函数
- 门禁评估：本地计算

## 残留风险

1. **maven_test 无 per-case 数据**：MavenTestOutcome 不含 failedCases，maven 项目仍用合成名，Flaky 检测降级。PRD 6.7 已知限制（"依赖功能一：用例库是用例级历史通过率的前提"）。
2. **vitest 项目 failedCases 为空**：vitest 解析不产出 per-case 失败名称（仅 TAP 解析产出），rerun 只能用聚合结果。首期可接受。
3. **重跑成本**：对每个可疑用例重跑 5 次全套件。用例数多时耗时较长。首期只对可疑用例重跑（非全量），成本可控。
4. **用例标题模糊匹配精度**：includes 双向匹配可能误匹配（短标题被长标题包含）。首期可接受，二期可加精确匹配+编辑距离。
