## Round 2 修复（review round 1 问题）

### P1-1: taskId 从未传入 saveCase → 已修复

**问题**：`saveCase(testCase, taskId?)` 的 `taskId` 参数从未被传入，`StoredCase.taskId` 和 `CaseVersion.taskId` 恒为 undefined，PRD 5.5 场景A"关联任务 ID"未满足。

**修复**：
1. `types.ts`：`AgentRunContext` 新增 `taskId?: string` 字段
2. `worker-mode.ts`：`adapter.run()` 传入 `{ taskId: task.taskId }`
3. `host-mode.ts`：`runExecute()` 传入 `{ taskId: message.executionId }`
4. `runner.ts` `runExecute()`：`execLibrary.saveCase(c, context?.taskId)` 传递 taskId

**验证**：`cases.test.ts` 新增测试 "stores taskId in StoredCase and CaseVersion" + "omits taskId when not provided"

### P1-2: computeCodeHash depth>3 限制遗漏深层源文件 → 已修复

**问题**：`computeCodeHash` 的 `walk` 函数在 `depth > 3` 时返回，Java Maven 布局 `src/main/java/com/company/Service.java` 中 `com/` 及以下（depth 4+）不被 hash，导致 Java 项目 codeHash 恒定，场景 A/B 失效。

**修复**：移除 `if (depth > 3) return;` 限制。EXCLUDE_DIRS + 隐藏目录跳过已防止无限递归。

**验证**：`cases.test.ts` 新增测试 "hashes deeply nested source files (Java Maven layout, depth 6+)"，验证 depth 6 的 `src/main/java/com/company/Service.java` 被正确 hash，内容变更时 codeHash 改变。

### P1-3: 场景B 文件级复用粒度无法保证≥80% → 已知限制（不扩大范围）

**问题**：`findReusableCases` 按 per-file hash 比较，若用例 target 指向变更文件则被丢弃。当多数用例指向同一变更文件时，复用率可能远低于 80%。

**处理**：按"不扩大范围、最保守方案"，文档记录为已知限制。方法级 hash 提取属二期，不在片1实施。文件级复用是 PRD 5.8 退路的明确选择（"hash 变则强制新生成"）。[需人工复核-场景B复用率预期]

### P2-4: Scout LLM 在 100% 命中时仍执行 → 已修复

**问题**：`run()` 中 `runScout` 在 `runCaseDesign` 之前执行，100% codeHash 命中时 scout LLM 仍跑。

**修复**：`runner.ts` 新增 `checkLibraryReuse()` 私有方法，在 `run()` 中 scout 之前检查库命中。命中时直接跳到 `runExecute`，跳过 scout + case-designer LLM。

### P2-5: GUI reason 字段 'edit' 与 core 'save' 不一致 → 已修复

**修复**：`main/index.ts` `saveCaseToLibrary` 中 `reason: existing ? 'save' : 'initial'`（原为 `'edit'`），与 `cases.ts` 对齐。

### P2-6: GUI saveCaseToLibrary 不刷新 index → 已修复

**问题**：GUI 的 `saveCaseToLibrary`/`deleteCaseFromLibrary` 不更新 `index.json` 的 `caseCount`/`lastUpdatedAt`。

**修复**：新增 `refreshCasesIndex(projectPath)` 函数，在 `saveCaseToLibrary` 和 `deleteCaseFromLibrary` 写文件后调用，重算活跃用例数并更新索引。

### P2-9: 新增用例未标记"增量" → 已修复

**修复**：
1. `types.ts`：`TestCase` 新增 `source?: 'reuse' | 'incremental' | 'generated'`
2. `runner.ts`：场景 A 100% 命中 → 标记 `source: 'reuse'`；场景 B 增量合并 → 旧用例 `source: 'reuse'`，新生成 `source: 'incremental'`
3. `runCaseDesign` 和 `runPlan` 两个路径均已更新

### P2-10: 需求 ID 字段未添加 → 已修复

**修复**：`types.ts` `TestCase` 新增 `requirementId?: string`（PRD 5.3"可选，首期留字段不强制"）。

### P2-7: 无 runner 级复用集成测试 → 已知限制

Runner 级集成测试需 mock @cxmt/agent-core Agent + LLM streaming，属扩大范围。CaseLibrary 单元测试（37 个）已覆盖复用判定的数据层逻辑。runner.ts 中的复用逻辑是简单条件分支，通过代码审查验证正确性。[需人工复核-runner级集成测试]

## 设计决策

### 1. 存储布局

```
.test-agent/cases/<projectHash>/
  index.json              # { projectHash, codeHash, fileHashes, lastUpdatedAt, caseCount }
  cases/
    <caseId>.json         # StoredCase（含完整版本历史）
```

- `projectHash` = SHA-256(规范化路径) 前 16 字符
- `caseId` = SHA-256(projectHash + ":" + title) 前 16 字符，跨运行稳定
- 每个用例一个 JSON 文件，内含 `history: CaseVersion[]` 完整版本历史

### 2. 代码指纹

`computeCodeHash(projectPath)` 遍历源文件（排除测试文件、node_modules、.test-agent 等），
对每个文件内容取 SHA-256 前 8 字符，再对排序后的 "path:hash" 拼接取 SHA-256 前 16 字符。

**无深度限制**（round 2 修复 P1-2）：Java Maven `src/main/java/com/company/` (depth 6+) 可正确 hash。

返回 `{ codeHash, fileHashes }`：
- `codeHash`：整体指纹，匹配则跳过 LLM（场景 A）
- `fileHashes`：per-file hash 映射，驱动文件级增量复用（场景 B）

### 3. 复用逻辑（runner.ts）

**run() 一次性路径**（worker-mode 用）：
1. `checkLibraryReuse()` — codeHash 匹配 + 库有用例 → 跳过 scout + case-designer，直接 runExecute（review P2-4）
2. 不匹配 → scout → case-designer → runExecute

**计划阶段（runCaseDesign / runPlan）**：
1. 计算 currentCodeHash
2. 查库 getStoredCodeHash()
3. codeHash 匹配 → 复用全部用例（标记 `source: 'reuse'`），跳过 LLM（场景 A：hit 100%）
4. codeHash 不匹配 → 调 LLM 生成，然后合并：
   - findReusableCases(currentFileHashes) 找 target 文件未变的旧用例
   - 去重合并：旧用例（标记 `source: 'reuse'`）+ 新生成用例（标记 `source: 'incremental'`）
   - 场景 B：文件级复用（同文件用例被丢弃，≥80% 不保证 — 见 P1-3 已知限制）
5. 用例 ID 重分配为稳定 hash（projectHash + title）

**执行阶段（runExecute）**：
1. 执行完成后，所有用例 `saveCase(c, context?.taskId)` 入库（taskId 写入 CaseVersion）
2. updateCodeHash 记录当前代码指纹
3. 写入失败不阻断主流程（降级跳过）

### 4. 版本历史

每次 saveCase/deleteCase/rollback 追加一条 CaseVersion 到 history 数组：
- `initial`：首次创建
- `save`：内容更新（GUI 和 core 统一使用 'save'，review P2-5 修复）
- `delete`：软删除（deleted=true，文件不删）
- `rollback`：回滚到历史版本（追加新版本，不删历史）

场景 C 验收：getHistory() 返回完整版本列表，rollback(caseId, version) 恢复指定版本。

### 5. GUI 集成

GUI 主进程自含实现（与 cases.ts 同格式，避免跨包 dist 依赖）：
- `cases:load` → 读取 `.test-agent/cases/<projectHash>/cases/*.json`
- `cases:save` → 写入用例（含版本历史）+ `refreshCasesIndex` 更新索引（review P2-6 修复）
- `cases:delete` → 软删除 + `refreshCasesIndex` 更新索引

App.vue 三个编辑函数改为读写库：
- `deleteCase(index)` → 调 `deleteCaseFromLibrary(projectPath, title)` + splice
- `addCase()` → 调 `saveCase(projectPath, newCase)` + push
- `updateCase(index, field, value)` → 更新内存 + 调 `saveCase(projectPath, item)`

写入失败不阻断 UI（`.catch(() => {})` 降级）。

## 残留风险

1. **computeCodeHash 性能**：遍历所有源文件并计算 hash（无深度限制后遍历更完整），大项目可能较慢。P0 可接受（计划阶段一次性计算，LLM 调用更慢）。
2. **target 字段质量**：增量复用依赖 LLM 生成的 target 字段包含文件路径。若 target 为方法名/API 路径（无法映射文件），保守复用（不跳过）。
3. **场景B ≥80% 复用率不保证**：文件级粒度下，同文件用例全部丢弃。[需人工复核-场景B复用率预期]
4. **GUI 跨包格式同步**：GUI 主进程自含用例库文件操作，与 cases.ts 同格式但独立实现。若格式变更需同步两处。
5. **并发写入**：单 Worker 进程内串行调用，无并发写入防护。多 Worker 同时写同一项目用例库可能冲突（P0 不涉及，多 Worker 分片在片4）。
6. **无 runner 级集成测试**：需 mock LLM 才能测试 runner 复用短路，属扩大范围。[需人工复核-runner级集成测试]
